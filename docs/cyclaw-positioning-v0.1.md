# cyClaw 产品定位说明 v0.2

日期：2026-07-04

## 1. 核心定位

cyClaw 的新定位是：

> cyClaw 是 AI Coding 时代的项目知识维护层。它自动发现代码变化和开发过程中的重要知识，并把它们沉淀成可维护、可检索、可复用的项目记忆。

更面向用户的表达：

> 让项目文档跟上每一次代码变化。

更面向 AI 协作的表达：

> Codex 改代码，cyClaw 维护项目记忆。

更完整的产品描述：

> cyClaw 不是另一个帮你写代码的 AI 工具，而是项目知识资产维护助手。它监听代码、配置、依赖和开发过程中的关键变化，自动判断哪些信息值得沉淀，生成文档更新建议，并帮助人和后续 AI 快速检索这些项目知识。

## 2. 定位来源

在日常使用 Codex、Claude Code、Cursor 等 AI 编码工具时，会出现一个越来越明显的问题：

- AI 能快速修改代码，但不会自然地维护项目文档。
- 开发者一开始可能会提醒 AI “边编码边写文档”，但长任务推进后很容易忘记。
- AI 通常只会完成当前编码目标，不会主动判断某个知识是否值得写入长期文档。
- 很多重要信息只存在于对话、终端输出、临时分析和开发者脑中。
- 下一次处理类似问题时，又要重新解释、重新分析、重新踩坑。

这说明 AI Coding 带来的新矛盾不是“代码写得不够快”，而是：

> 代码生产效率提升后，项目知识资产维护跟不上。

cyClaw 要解决的就是这个断层。

## 3. 产品边界

cyClaw 不主打：

- 替你写代码。
- 替你重构项目。
- 替你完成所有办公任务。
- 成为通用个人 AI 助手。
- 成为全能 Agent 操作系统。

cyClaw 主打：

- 发现代码变化背后应该同步的知识。
- 捕获开发过程中值得沉淀的重要信息。
- 维护项目文档、规则、决策和经验。
- 让项目知识可以被人和 AI 检索复用。

一句话边界：

> cyClaw 关注代码之外，但开发必须长期维护的项目知识。

## 4. 差异化价值

### 4.1 不和 Codex / Claude Code 正面竞争

Codex、Claude Code、Cursor 等工具的强项是：

- 读代码。
- 改代码。
- 跑命令。
- 修错误。
- 生成测试。
- 提交变更。

cyClaw 的强项应该是：

- 发现本次代码变更影响了哪些知识资产。
- 判断哪些开发过程信息值得长期保存。
- 生成文档更新草稿。
- 检测文档和代码是否漂移。
- 维护给人和 AI 使用的项目记忆。

二者的关系不是替代，而是互补：

```text
AI 编码工具负责改变项目
cyClaw 负责解释、记录和沉淀这些改变
```

### 4.2 从“文档生成”升级为“知识维护”

普通 AI 文档工具解决的是：

> 根据代码生成一份文档。

cyClaw 要解决的是：

> 在项目持续变化时，判断哪些知识应该被更新、补充、校验和检索。

差别在于：

- 文档生成是一次性的。
- 知识维护是持续性的。
- 文档生成关注内容产出。
- 知识维护关注真实性、完整性、可追溯和可复用。

### 4.3 形成长期项目记忆

代码变更是短期价值，知识沉淀是长期价值。

cyClaw 维护的内容越多，项目越清晰：

- 新人更容易接手。
- 后续 AI 更容易理解项目。
- 重复踩坑减少。
- 架构决策有迹可循。
- 项目交接不再依赖口头说明。

## 5. 核心能力

cyClaw 第一阶段建议收敛为 4 个核心模块：

```text
变更雷达 + 知识捕获器 + 文档维护器 + 知识检索器
```

### 5.1 变更雷达

回答的问题：

> 代码变了，哪些文档或知识资产应该同步？

典型能力：

- 扫描 Git diff。
- 识别 API、Schema、依赖、配置、目录结构等变化。
- 判断受影响的文档。
- 生成更新建议。
- 在提交前提醒缺失的文档更新。

示例：

```text
本次变更修改了 2 个接口和 1 个数据模型，但没有更新相关文档。
建议生成 API 文档和 Schema 文档更新草稿。
```

### 5.2 知识捕获器

回答的问题：

> 开发过程中出现了哪些重要认知，值得沉淀？

典型能力：

- 从 AI 对话、任务总结、终端输出、代码 diff 中提取高价值信息。
- 判断信息的重要性。
- 推荐写入位置。
- 进入知识收件箱等待确认。

可捕获的知识类型：

| 知识类型 | 示例 | 推荐写入位置 |
| --- | --- | --- |
| 技术决策 | 为什么选择某个库、方案、架构 | `docs/adr/` 或 `docs/decisions.md` |
| 踩坑经验 | 某个依赖版本不兼容，最终如何解决 | `docs/troubleshooting.md` |
| 业务规则 | 某字段不能为空、某状态不能直接流转 | `docs/domain-rules.md` |
| 项目约定 | 命名规则、接口返回格式、目录放置规则 | `docs/conventions.md` |
| 环境细节 | 本地启动必须先配置某变量 | `docs/environment.md` |
| 调试方法 | 如何复现、定位、验证某类问题 | `docs/debugging.md` |
| 第三方限制 | API 限流、SDK 缺陷、平台兼容性 | `docs/integrations.md` |
| AI 协作经验 | 某类任务应该先读哪些文件、跑哪些命令 | `.cyclaw/memory.md` |

### 5.3 文档维护器

回答的问题：

> 如何让文档持续准确，而不是生成后就过期？

典型能力：

- 生成文档更新草稿。
- 展示文档 diff。
- 支持用户接受、编辑、忽略。
- 检测文档和代码不一致。
- 定期生成文档健康报告。

重点文档类型：

- API 文档。
- 数据库 Schema 文档。
- 依赖变更记录。
- 环境变量说明。
- 部署说明。
- 架构说明。
- 业务规则。
- 技术决策记录。
- 故障排查记录。
- 项目变更日志。

### 5.4 知识检索器

回答的问题：

> 这些沉淀下来的知识如何被人和 AI 重新使用？

典型能力：

- 从代码、文档、历史任务和知识收件箱中统一检索。
- 给出回答来源。
- 支持自然语言问答。
- 将关键知识整理成给 AI 使用的项目记忆。

示例问题：

- 这个项目的鉴权逻辑在哪里说明过？
- 订单状态流转规则是什么？
- 上次为什么升级 Vite？
- 这个环境变量是谁引入的？
- 修改用户表时需要同步哪些文档？
- 某个问题以前是否踩过坑？

## 6. 信息价值判断标准

cyClaw 不能把所有信息都写进文档，否则会制造噪音。建议使用以下标准判断一条信息是否值得沉淀：

1. 复用价值：未来是否可能再次用到。
2. 决策价值：是否解释了为什么这样做。
3. 排错价值：是否能帮助以后少踩坑。
4. 协作价值：新人或其他 AI 是否需要知道。
5. 约束价值：是否描述了不能违反的规则。
6. 变更价值：是否改变了项目结构、流程、依赖或接口认知。

满足任意 2 项，可以进入“知识收件箱”。

示例：

```text
候选知识：支付回调必须先校验签名，再更新订单状态。

重要性：高
原因：
- 涉及支付流程
- 影响数据一致性
- 未来修改订单逻辑时必须知道

建议写入：docs/domain-rules.md
```

## 7. 产品交互原则

### 7.1 不静默写入

cyClaw 应该主动发现知识，但不应该默认静默写入所有文档。

推荐交互：

```text
cyClaw 发现 3 条可能值得沉淀的项目知识：

1. 当前支付回调必须先校验签名再更新订单状态
   建议写入：docs/domain-rules.md

2. Vite 版本升级后需要同步调整插件配置
   建议写入：docs/troubleshooting.md

3. 本项目接口错误码统一从 10000 开始
   建议写入：docs/conventions.md

操作：接受全部 / 逐条查看 / 编辑 / 忽略
```

### 7.2 先进入知识收件箱

所有候选知识先进入知识收件箱。

每条记录包含：

- 摘要。
- 来源。
- 推荐写入位置。
- 重要性等级。
- 关联文件。
- 关联任务。
- 接受、编辑、忽略、稍后处理。

### 7.3 所有更新都可追溯

每次文档更新都应该记录：

- 来源任务。
- 关联代码变更。
- 生成原因。
- 用户确认状态。
- 写入的目标文档。

## 8. MVP 范围

第一版不做完整 Coding Agent，只做“项目知识维护”的最小闭环。

核心流程：

```text
扫描项目 -> 读取 Git diff -> 识别变化 -> 判断知识影响 -> 生成候选知识 -> 用户确认 -> 写入文档 -> 支持检索
```

### 8.1 首批检测规则

| 变更类型 | 触发建议 |
| --- | --- |
| 新增或修改 Controller、Route、OpenAPI 注解 | 更新 API 文档 |
| 修改 Entity、Model、Migration、SQL 文件 | 更新 Schema 文档 |
| 修改 `package.json`、`pom.xml`、`requirements.txt`、`go.mod` | 更新依赖记录 |
| 修改 `.env.example`、配置类、配置文件 | 更新环境变量和部署说明 |
| 新增模块、移动目录、重命名核心文件 | 更新架构说明 |
| 长任务完成后产生关键结论 | 进入知识收件箱 |
| 提交前存在代码变更但无文档更新 | 提醒生成文档草稿 |

### 8.2 首批知识资产

建议第一版维护以下文件：

```text
docs/api.md
docs/schema.md
docs/dependencies.md
docs/environment.md
docs/architecture.md
docs/conventions.md
docs/troubleshooting.md
docs/domain-rules.md
.cyclaw/memory.md
.cyclaw/knowledge-inbox.json
```

### 8.3 首批页面

第一版界面建议围绕“项目知识面板”设计，而不是聊天框优先。

左侧：知识资产目录

- API
- Schema
- 架构
- 依赖
- 环境
- 约定
- 踩坑
- AI 记忆

中间：变更雷达

- 最近代码变更。
- 受影响文档。
- 建议更新项。
- 待处理知识。

右侧：更新草稿

- 更新原因。
- 推荐写入位置。
- 生成内容。
- diff 预览。
- 接受、编辑、忽略。

### 8.4 MVP 成功标准

第一版只要做到以下几点，就算方向成立：

- 能从 Git diff 中识别 3 到 5 类高价值变更。
- 能准确建议应该更新哪些知识资产。
- 能生成可用的文档草稿。
- 能把开发过程中的关键结论放入知识收件箱。
- 能让用户确认后写入文档。
- 能根据已有知识回答项目问题并给出来源。

## 9. 后续增强功能

### 9.1 文档健康度检查

定期扫描项目，给出文档健康度：

- 哪些文档过期。
- 哪些模块没有文档。
- 哪些 API 缺少说明。
- 哪些配置没有解释。
- 哪些文档引用了不存在的文件或字段。

### 9.2 文档漂移检测

对比文档描述和当前代码实现，发现不一致：

- 文档说接口字段是 `name`，代码已经改成 `displayName`。
- 文档说需要 Node 18，实际 `package.json` 要求 Node 20。
- 文档说有某个环境变量，但代码已经不再读取。

### 9.3 任务结束自动复盘

每次 Codex 或 cyClaw 完成长任务后，自动生成复盘问题：

- 本次任务改变了哪些项目认知？
- 哪些文档需要更新？
- 是否产生新的约定？
- 是否遇到值得记录的坑？
- 是否有新的验证方式？

### 9.4 面向 AI 的项目记忆

除了给人看的文档，还要维护给 AI 看的记忆：

```text
.cyclaw/memory.md
.cyclaw/project-rules.md
.cyclaw/task-playbooks/
```

这些文件告诉后续 AI：

- 本项目的固定约定。
- 常用命令。
- 不要重复踩的坑。
- 修改某类文件后必须同步更新哪些文档。
- 处理某类任务时应该先读哪些文件。

### 9.5 Git Hook 和 IDE 插件

在提交前提示：

```text
本次提交修改了 2 个接口和 1 个数据模型，但没有更新相关文档。
是否生成文档更新草稿？
```

这可以作为后续 Git Hook、IDE 插件或桌面端能力。

## 10. 推荐口号

候选口号：

1. 让项目文档跟上每一次代码变化。
2. Codex 改代码，cyClaw 维护项目记忆。
3. 自动捕获开发过程中的重要知识。
4. 让代码之外的项目知识不再丢失。
5. AI Coding 时代的项目知识维护层。

当前最推荐：

> 让项目文档跟上每一次代码变化。

原因：

- 用户一眼能懂。
- 痛点明确。
- 不抽象。
- 能覆盖变更雷达、文档维护和知识捕获。

## 11. 结论

cyClaw 当前最值得坚持的定位是：

> AI Coding 时代的项目知识维护层。

它解决的问题不是“如何更快写代码”，而是：

> 当 AI 让代码变化越来越快时，如何让项目知识不丢失、不漂移、可追溯、可检索、可复用。

第一版应该聚焦一个清晰闭环：

```text
发现变化 -> 捕获知识 -> 生成建议 -> 用户确认 -> 写入文档 -> 支持检索
```

这个定位足够具体，和现有 AI 编码工具形成互补，也有持续演进空间。
