# cyClaw Agent 开发面试拷打与参考答案

> 适用对象：cyClaw v0.1.6。本文用于模拟大厂 Agent 开发岗位的项目面试，而不是产品宣传稿。
>
> 使用原则：每个答案均区分“已实现”“局限”和“下一步”。被追问时先讲可被代码和测试证明的事实，再说明边界，不能把设计愿景说成线上能力。

## 0. 先校准项目事实

| 项目事实 | 面试时应如何说 |
| --- | --- |
| 工作区规模 | 当前 `Cargo.toml` 列出 **13 个 crate**，不应继续称为 12 个。 |
| 核心定位 | 面向 Coding Agent 与开发团队的本地优先“项目知识观察器与治理器”。Coding Agent 完成当前代码任务，cyClaw 独立维护跨会话、跨 Agent 的可验证项目知识。 |
| 自主性 | `cyclaw observer run` 启动时补偿扫描，之后监听文件系统事件，以 Git 快照确认真实变化；它不依赖 Codex、Claude Code 或人工调用 MCP。 |
| 写入边界 | Observer 自动生成候选、更新本地索引、验证事实和产生对账报告；不自动改业务代码和项目文档。文档与 Fact 的变更必须经受控 Patch 流程。 |
| 现实阶段 | 这是本地单项目的 v0.1.6，不是已证明可承载千级 Agent 的云服务。 |

### 30 秒开场回答

“cyClaw 不是第二个 Coding Agent，也不是给仓库加一个 RAG。它以独立 Observer 旁路观察代码、Git 状态、测试报告和已有事实的证据漂移，把可验证事件沉淀为候选知识，再通过事实账本、对账和受控 Patch 治理重复、冲突与过期信息。Codex 或 Claude Code 优化一次任务的推理和代码修改；cyClaw 优化项目生命周期中知识是否可信、是否可追溯、下一次任务是否能拿到最小有效上下文。”

### 架构图

```text
文件系统事件 / Git 工作区差异 / 测试构建报告
                    │
                    ▼
       独立 Observer：启动补偿、去抖、Git 快照确认
                    │
                    ▼
  变更分析 / 失败事件 / 带路径与哈希的候选知识
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
本地检索索引              Fact Ledger 与证据验证
        │                       │
        └───────────┬───────────┘
                    ▼
     duplicate / conflict / stale 对账建议
                    │
                    ▼
  人或 Agent 通过 MCP/CLI/IDE 预览、审批、应用、撤销 Patch
```

## 1. 定位、用户与竞争边界

### Q1：一句话讲清 cyClaw 解决什么问题？Codex、Claude Code 为什么不能直接替代？

**参考回答：**

它解决的是“项目知识长期失真”而不是“单次代码任务不会做”。Coding Agent 已擅长理解需求、改代码、跑命令、补文档，但它们的会话上下文、各次任务结论和人工修改之间天然断裂。cyClaw 的独立进程持续从项目状态采集证据，并以候选、事实、对账和 Patch 把知识纳入治理。

**代码依据：** `observe_project_once` 在启动时读取持久化状态并执行观察；CLI 的 `observer run` 持续触发观察。MCP 只是查询和受控治理入口，不是事件源。[`crates/cyclaw-core/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-core/src/lib.rs:1378) [`crates/cyclaw-cli/src/main.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-cli/src/main.rs:873)

**拷打追问：** “如果 Codex 自己也能写文档，你不就鸡肋了吗？”

**继续回答：** 如果 cyClaw 只在 Codex 调用后补一篇文档，确实鸡肋。因此当前设计把“发现”从 Agent 调用中剥离：它观察所有项目活动，包括人工 IDE 修改、其他 Agent 修改、测试报告失败和启动前遗留的未提交改动。它的价值是长期一致性和治理闭环，而不是替 Agent 续写 Markdown。

**诚实边界：** 当前候选主要来自规则化变更与报告信号，尚未证明在所有真实团队中能显著减少重复探索；需要用真实任务集做效果评测。

### Q2：目标用户是 Agent 还是开发者？真实需求怎么验证？

**参考回答：** 两者都是，但主用户旅程不同。Observer 的用户是项目本身，它无需等 Agent 调用；Fact、Patch 和对账报告服务于开发者审阅和任意 Coding Agent 的读取。成功指标不应是“生成了多少文档”，而应是候选精确率、事实漂移发现率、重复知识减少量、任务开始时上下文命中率与人工审阅成本。

**不要硬说：** 没有调研样本和 A/B 数据时，不能虚构“开发者愿意常驻进程”或“效率提升百分比”。正确回答是把这列为下一阶段试点假设，并采集安装留存、禁用率、候选接受率和误报原因。

### Q3：什么是文档熵增，怎么量化？

**参考回答：** 熵增不是主观感受。可操作的定义是：同一事实多处表述、证据已漂移仍被引用、已被替代的决策缺少关系、任务上下文中混入无关或互相矛盾的信息。现有对账输出 `duplicate`、`conflict`、`stale` 建议，并映射到 `merge`、`supersede`、`delete`，但尚未形成跨项目长期趋势仪表盘。

**下一步指标：**

- 重复率：`duplicate / active facts`。
- 漂移率：验证失败事实占比与平均发现时延。
- 治理收益：合并、取代、删除后减少的上下文 Token。
- 人工成本：候选接受率、平均审阅时长、误报关闭原因。

### Q4：为什么用 Rust，而不是 Java 或 TypeScript？

**参考回答：** 选择 Rust 是为本地常驻观察器服务：单二进制分发、较低空闲资源、跨平台文件系统与进程控制、类型化的错误处理。它不是因为 Rust 自动解决一致性问题；一致性仍来自锁、事务文件、状态机、哈希与恢复流程。Rust 的所有权主要降低共享可变状态和内存生命周期错误的风险，不能替代产品层的并发协议。

**追问应答：** 工作区声明 Rust 1.85、edition 2024；应实际执行 `cargo clippy`、审查 `unsafe` 使用，而不要只说“内存安全”。本项目不应在未审计前宣称“零 unsafe”或“文件操作绝对原子”。[`Cargo.toml`](/D:/Git/Job%20Search%20Preparation/cyClaw/Cargo.toml:1)

### Q5：与通用 Memory/RAG 产品相比，差异和劣势是什么？

**参考回答：** 通用 Memory 重点是存储和语义召回；cyClaw 的重点是项目内知识的证据、时效和治理操作。每条可长期使用的事实需要回答“证据在哪、是否仍然成立、被谁取代、能否撤销”。劣势也明确：当前本地规则检索与启发式对账在语义理解、跨仓库知识图谱、云端协作和海量规模上都弱于成熟平台。

## 2. Agent 记忆、证据与召回

### Q6：记忆分层是什么，为什么不能只存一个 facts.jsonl？

**参考回答：** 至少分四层：

| 层 | 内容 | 生命周期 |
| --- | --- | --- |
| 事件层 | 文件变化、执行失败、Patch 操作 | 追加审计，可追溯 |
| 候选层 | 值得沉淀但尚未确认的信号 | 可接受、忽略或过期 |
| 事实层 | 经审阅的行为、决策、失败经验 | 跨会话召回，证据可验证 |
| 任务层 | 当前目标、检查点、上下文包 | 任务内使用，关闭后保留摘要/事实 |

不分层会让测试失败日志、未经验证的推断和稳定约束混在一起，检索时既污染上下文，又无法定义不同的失效与审批策略。

### Q7：FactEvidence 为什么要带路径、符号、行范围、内容哈希和 Git 提交？

**参考回答：** 这些字段对应不同粒度的可验证性：路径定位载体，符号和行范围缩小解释范围，内容哈希检测证据内容是否变化，Git 提交帮助回溯产生时的代码版本。验证不是“相信历史记录”，而是重新读取当前证据并生成验证结果。文件删除、哈希不一致或无法读取应当成为漂移/失效信号，而不是静默继续召回。

**代码依据：** `FactEvidence` 与 `FactEvidenceVerification` 是独立结构，`verify_evidence` 被事实验证流程调用。[`crates/cyclaw-memory/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-memory/src/lib.rs:195) [`crates/cyclaw-memory/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-memory/src/lib.rs:1028)

**边界：** 证据哈希证明“内容变了”，不自动证明“事实一定错了”。例如重构行号但语义未变，仍需要对账或人工判断。

### Q8：跨会话召回如何工作？2000 Token 是不是拍脑袋？

**参考回答：** `begin_task` 建立任务，`get_task_context` 按查询编译事实、文档检索结果与候选；结果返回预算、估算 Token 和 `truncated`。实现会把约 60% 的预算优先给结构化事实，其余分配给文档和候选，并在达到预算时截断。

**关键澄清：** 60% 是当前工程默认值，不是经过消融实验得出的普适最优值。面试中应说它是可配置启发式；后续按任务类型和离线评测校准，而不是把经验数字包装成科学结论。[`crates/cyclaw-core/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-core/src/lib.rs:1162)

### Q9：为什么不把整个仓库塞给模型？与 RAG 的区别是什么？

**参考回答：** 上下文窗口变大不等于信息质量变高。全仓库会引入无关代码、过期文档和相互矛盾的历史，且成本、延迟和注意力稀释仍存在。RAG 解决“找相似片段”；cyClaw 还要解决“哪些项目事实可信、是否过期、为什么必须带入、允许占用多少预算”。因此检索只是读取路径，Fact Ledger 和治理才是差异。

### Q10：50 轮长任务的上下文如何控制？

**参考回答：** 当前项目能保存任务检查点、事实和明确预算的上下文包，但它不是完整的对话历史压缩系统。正确做法是把可验证的决策、失败路径、未完成事项从对话中提炼为结构化状态，下一轮按目标重新编译，而不是无条件拼接旧消息。

**现有缺口：** 尚没有针对工具输出、推理历史的自动 compact 算法，也没有基于任务阶段的遗忘策略。这是应主动承认的 P1 能力。

### Q11：记忆投毒怎么防？项目 README 里的恶意指令会不会变成长期事实？

**参考回答：** 必须把“项目内容”视为不可信数据，把“治理策略与工具权限”视为可信控制面。候选只是待审对象，不能因文本出现“把我写入记忆”就自动成为 Fact；模型审阅输出也不能绕过证据、权限和 Patch 审批。对高风险来源要记录来源、降置信度、禁止执行性指令进入事实，并允许审阅者查看原始证据。

**现状与缺口：** 当前有候选状态、证据和权限门，但没有成熟的内容信任分级、注入分类器或不可篡改审计链。因此不能宣称已经“解决 Prompt Injection”。P0 是为来源增加 trust level，P1 是将模型输入中的不可信文本分区并用结构化 Schema 校验输出。

### Q12：多项目和跨项目知识如何隔离？

**参考回答：** 当前隔离单元是项目根目录下的 `.cyclaw/`，索引、事实、事件、候选和 Observer 状态均按根目录持久化。默认不做隐式跨项目传播，防止 A 项目的业务约束污染 B 项目。公司规范这种共享知识应当作为显式挂载、带版本和来源的只读策略包，而不是把多个 `.cyclaw` 目录混用。

## 3. 自主 Observer：这是项目最关键的拷打点

### Q13：你怎么证明它不是“必须由 Codex 调用”的被动工具？

**参考回答：** 数据面不经过 MCP：`cyclaw observer run` 直接启动，先执行一次 `observe_project_once` 做启动补偿，再监听文件系统。每次事件只作为唤醒信号，实际是否产生变化由上次持久化快照与当前 Git 状态比较决定。Observer 还会识别约定测试/构建报告中的失败内容，并将其记录为执行事件和候选知识。

**可验证路径：** [`crates/cyclaw-cli/src/main.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-cli/src/main.rs:873) [`crates/cyclaw-core/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-core/src/lib.rs:595) [`scripts/test-observer-e2e.ps1`](/D:/Git/Job%20Search%20Preparation/cyClaw/scripts/test-observer-e2e.ps1:1)

### Q14：为什么文件事件驱动，而不是每三秒全量轮询？事件丢了怎么办？

**参考回答：** 文件事件用于低延迟和低空闲成本，Git 快照用于确认与去重。事件可能重复、乱序甚至丢失，所以事件本身不能被当作事实；它只是触发重新计算。启动补偿扫描可以覆盖进程未运行期间的未提交改动，持久化 `ObserverState` 使重启后能继续使用上次快照。

**关键边界：** 当前实现没有“永久保证每一个文件事件至少一次”的持久化消息队列。若 Observer 运行中事件丢失且没有后续事件或重启，变化不一定立刻被发现。生产级改进是增加定期低频校验、持久事件日志与 cursor/ack，而不是声称 Git 快照已经解决所有丢事件问题。

### Q15：如何避免 cyClaw 写自己的 `.cyclaw` 文件后不断触发自己？

**参考回答：** 变更雷达在快照与分析阶段排除 `.cyclaw/`，并排除 `target/`、`node_modules/`、`build/`、`dist/`、`.gradle/` 等生成目录。这样 Observer 生成索引、候选和测试构建产物不会反过来被当成用户源码变化。

**真实复盘：** E2E 曾暴露构建报告位于 `target` 时被纳入 Git 快照、导致重复 tick。修复是在变更雷达统一过滤生成目录，并用“修改依赖、写入失败报告、重启后无变化”黑盒流程回归。这比泛泛回答“做了去抖”更有说服力。[`crates/cyclaw-change-radar/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-change-radar/src/lib.rs:1)

### Q16：测试/构建报告是怎么发现的？文本匹配会不会误报？

**参考回答：** 当前实现识别约定目录，例如 Surefire、JUnit、测试报告目录，并检查失败/错误信号，生成带来源文件的 `ExecutionEvent`。同一事件再次记录时会去重，避免同一失败重复淹没候选箱。

**边界：** 这是启发式发现，不是完整 CI 适配器。它可能漏掉自定义报告、把无关文本误判为失败，也无法理解失败根因。下一步应优先接入 JUnit、Surefire、pytest、cargo test 等结构化解析器，抽取测试名、失败栈、退出码和关联文件。

### Q17：Observer 进程崩溃、机器重启后如何恢复？

**参考回答：** 它把观察快照和维护计数存入 `.cyclaw/observer-state.json`；启动时先初始化/扫描所需资产，再以已有状态进行观察，最终写回新状态。Windows 可通过 `observer install` 注册登录后启动。事实 Patch 的恢复与 Observer 状态是两件事：前者有专门事务恢复，后者目前只是状态文件持久化。

**边界：** `observer-state.json` 当前不是带临时文件 rename 的原子写协议，也没有 watchdog、指数退避和健康上报。因此“能重启补偿”已实现，“进程永不掉线”未实现。P0 是原子状态写入、损坏状态回退与监督进程；P1 是健康指标和告警。

## 4. 知识治理、事务与一致性

### Q18：为什么要有 create/update/merge/supersede/delete 五种操作？为什么不直接改文本？

**参考回答：** 追加只会制造重复，直接覆盖会丢掉决策历史。`create` 处理缺失知识，`update` 同步仍有效事实，`merge` 消除重复，`supersede` 保存旧决策并建立取代关系，`delete` 移除有害且不应保留的内容。它们使治理意图成为数据模型的一部分，而不是一段不可解释的字符串替换。

**追问：** “delete 是物理删还是软删？”

**继续回答：** 文档 Patch 的目标文本可以删除，但 Patch 自身保留 before snapshot、状态和审计事件，支持撤销。Fact 层的最终保留策略、软删除清理与 retention 还需要明确的生命周期策略，不能混同为已经完成的合规归档系统。

### Q19：duplicate、conflict、stale 如何识别？为什么不自动执行？

**参考回答：** 当前对账是确定性与启发式规则生成建议：重复通常建议 merge，冲突建议 supersede，证据漂移或失效建议 delete。它不自动修改事实状态，因为“文本相似”“文件变了”不等于“语义可以安全合并或删除”。人工或受控 Agent 必须核对证据后创建 Patch。

**追问回答：** 自动化可从低风险、确定性场景开始，例如完全相同内容和完全相同证据的去重提示；但仍应保留可预览、可撤销和审计。不要在 v0.1 阶段开启语义自动 merge。

### Q20：两个 Agent 并发修改同一事实，如何保证不损坏？

**参考回答：** 需要分开讲“文件完整性”和“语义冲突”。项目级锁用来串行化本地写操作；Fact Patch 用 `Pending -> Applying -> Applied` 或撤销状态机，并在操作前恢复遗留事务。Patch 保存操作前快照和目标指纹，应用/撤销时发现目标已经被他人改动会拒绝覆盖，避免静默丢数据。

**代码依据：** [`crates/cyclaw-memory/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-memory/src/lib.rs:1375) [`crates/cyclaw-memory/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-memory/src/lib.rs:1474)

**边界：** 本地锁和 JSON 文件事务不是分布式共识。跨机器、共享网络盘、千级 Agent 需要中心化事件账本、乐观版本号、租约和服务端幂等键。

### Q21：Patch 中途崩溃怎么恢复？为什么 revert 要校验指纹？

**参考回答：** 先落盘事务描述，再进入 Applying/Reverting，完成后更新 Patch 状态并清除事务。启动或下一次操作会调用 `recover_fact_patch_transactions`：能判断并恢复的事务标记完成；无法安全恢复的产生 blocked 报告，避免继续在不确定状态上写入。撤销校验指纹，是为了不把开发者在 Patch 生效后做的后续修改粗暴覆盖掉。

**高分点：** 这不是数据库意义上的全局 ACID；它是本地文件系统下的可恢复 Saga。答题时应说明原子边界、失败报告和人工介入路径。

### Q22：审计记录什么？能防篡改吗？

**参考回答：** Patch 本身包含创建、应用、撤销等审计事件，项目还有追加事件日志记录项目扫描、候选、Patch 等关键动作，因此可以回答“某个 Patch 在什么时候从什么状态变成什么状态”。[`crates/cyclaw-events/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-events/src/lib.rs:171)

**边界：** 本地 JSONL 是可追溯日志，不是防篡改审计。拥有项目目录写权限的人可以改它。若要满足安全审计，应引入 hash chain、签名、远端只追加存储和身份绑定。

## 5. MCP、权限与 Agent 安全

### Q23：为什么 MCP 用 stdio，而不是 HTTP/SSE？

**参考回答：** cyClaw 是本地项目工具，stdio 可以继承宿主 Agent 的进程生命周期和当前工作目录，不暴露本地端口，部署和权限面更小。HTTP/SSE 更适合多客户端、远程服务和长期共享会话，但会带来认证、租户隔离、端口暴露与服务运维问题。

**关键架构点：** MCP 是控制面和读取面，Observer 是独立数据面。即使 MCP 未被任何 Agent 启动，Observer 仍可采集变化；反过来 MCP 只暴露受控工具，而不是任意 Shell 或任意路径写入。[`crates/cyclaw-mcp/src/lib.rs`](/D:/Git/Job%20Search%20Preparation/cyClaw/crates/cyclaw-mcp/src/lib.rs:204)

### Q24：权限模型怎么划分？为什么不让模型直接写文档？

**参考回答：** 默认以本地知识写入为限，文档应用、模型调用、网络和自动化都需要显式策略。模型输出只可提出候选或草稿，真正应用文档须通过路径守卫、文档写入授权和 Patch 预览/应用流程。这样把“模型建议”与“改变用户项目”隔离。

**需纠正的旧说法：** 当前产品定位已取消 Observer 自动写 docs 的主路径；旧文档中的 `allow_auto_apply_docs` 表述应视为历史设计，不能作为现状宣传。以代码和最新定位文档为准。[`docs/cyclaw-positioning-v0.1.md`](/D:/Git/Job%20Search%20Preparation/cyClaw/docs/cyclaw-positioning-v0.1.md:1)

### Q25：API Key、配置篡改和 Prompt Injection 怎么处理？

**参考回答：** 项目配置只应存环境变量名等引用，而非明文密钥；模型调用失败要返回可操作错误，不能把密钥写入事件或缓存。配置文件本身属于本地信任边界，若攻击者能写项目目录，不能仅靠 YAML 保护它，因此高风险策略应在 IDE 信任、文件权限和必要时用户级 SecretStorage 中再次约束。

**Prompt Injection 的策略：** 不可信仓库文本仅作为证据，不是指令；模型输出用固定 Schema 解析；任何写入仍经过 policy 和 Patch；候选中保留来源供人工查看。当前没有完整恶意内容检测，这是明确风险而不是已解决能力。

### Q26：为什么 Git Hook 默认提示而非阻断？

**参考回答：** 知识候选包含启发式判断。默认阻断提交会把误报成本转嫁给所有开发者，最终导致用户卸载工具或绕过 Hook。严格模式只适合团队已验证候选精确率、并能定义极少数硬规则的场景。Observer 已承担异步发现职责，因此 Hook 应是最后提醒，而不是唯一采集链路。

## 6. 架构、检索、性能与规模

### Q27：13 个 crate 的边界如何划分，如何避免“为了 Rust 而拆 crate”？

**参考回答：** 拆分按稳定职责而非文件数量：`scanner` 认识项目结构，`change-radar` 分析变化，`knowledge` 生成候选，`memory` 管理任务/事实/Patch，`retrieval` 建本地索引，`events` 记录事件，`policy` 决定权限，`model` 封装模型调用，`mcp`/`cli`/IDE 是适配层，`core` 编排用例。边界的价值是让 Observer 编排不依赖具体 IDE，也让 Patch 事务不依赖 MCP 协议。

**面试官追问：** “循环依赖呢？”

**继续回答：** 依赖应单向从适配层指向核心能力；若 `memory` 反过来依赖 MCP 或 CLI，说明边界失败。实际回答前应展示 `cargo tree`，不要凭印象画依赖图。

### Q28：检索是关键词、向量还是混合？如何评价？

**参考回答：** 当前本地索引是轻量检索路径，核心优势不是向量召回，而是结果可追溯到路径、证据和事实状态。应避免宣传为“混合 RAG”或“语义搜索”，除非代码和离线基准确实实现。后续可加入 BM25、符号/路径特征、向量召回和 rerank，但必须保留可解释的来源与过滤失效事实。

**评测设计：** 建一个标注任务集，统计 Recall@k、MRR、事实过期过滤准确率与“被最终任务采纳”的比例；区分代码定位任务、架构决策任务、失败经验复用任务。

### Q29：百万行仓库、千级 Agent 并发时瓶颈在哪？

**参考回答：** 当前瓶颈首先在单项目文件扫描/Git diff、索引重建、JSONL/SQLite 的本地写入串行化和对账遍历，不在模型。千级 Agent 并发更超出本地目录锁的模型。演进路线是：

1. 保留路径级增量与生成目录排除，使用文件清单/内容签名降低扫描量。
2. 将事件写入持久队列，以项目分区和幂等键消费。
3. 把事实与审计迁移到支持事务和并发控制的服务端存储。
4. 用版本号、乐观并发控制、租约和死信队列替代本地文件锁。
5. 把对账变成异步分片作业，模型只审阅规则无法判定的少数样本。

**不要给出未经压测的 QPS、延迟和成本数字。**

### Q30：事件风暴、8MB 文件和符号链接怎么处理？

**参考回答：** 原则是事件合并、快照去重、生成目录过滤和资源上限。大文件不应完整读入并送给模型，符号链接不应无边界跟随到工作区外。当前设计文档已给出事件合并、容量和大文件签名方向；面试时要区分“已在变更过滤落地”与“事件队列背压、跨平台行为完整压测仍待补齐”。

## 7. 评测、可观测性与真实复盘

### Q31：你怎么证明 cyClaw 有效？

**参考回答：** 不能用“跑通 demo”证明有效。现有测试证明的是正确性下限：workspace 单测、CLI/插件检查、Observer 黑盒 E2E；它们验证启动补偿、源码修改、失败报告、候选去重和重启后增量恢复。有效性需要真实项目试点与人工标注：候选精确率、召回率、事实验证失败发现时延、任务上下文采纳率、治理后重复率和审阅耗时。

**推荐分层：**

| 层 | 目标 | 例子 |
| --- | --- | --- |
| 单元测试 | 状态机和边界条件正确 | Patch 崩溃恢复、证据哈希变化 |
| 集成测试 | crate 间协议正确 | 变更到候选、候选到 Patch |
| 黑盒 E2E | 自主运行闭环正确 | Observer 启动、重启、报告失败 |
| 离线评测 | 知识质量可量化 | 标注候选的 precision/recall |
| 试点观测 | 用户价值 | 采纳率、误报关闭、禁用率 |

### Q32：你遇到过最难的 bad case 吗？请按 STAR 讲。

**参考回答：**

- **S：** Observer E2E 中构建报告写入 `target` 后，观察器反复产生 tick。
- **T：** 目标是报告失败可被采集，同时系统不能因自身或构建产物无限自触发。
- **A：** 通过日志和快照对比定位到变更雷达将生成目录纳入 Git 快照；统一过滤 `.cyclaw`、`target`、`node_modules`、`build`、`dist`、`.gradle`，并让 E2E 断言恰好产生预期事件和重启后无变化。
- **R：** 修复后，修改项目文件只产生一次变更候选，测试报告只产生一次失败候选，重启不会重复发现同一变化。

这说明“notify 收到事件”不足以证明正确，必须验证事件源、快照、产物目录和重启边界的组合。

### Q33：可观测性够吗？出了错如何排查？

**参考回答：** 当前可查看 `.cyclaw` 中的事件、候选、Patch、对账报告和 Observer 状态，且 CLI/测试脚本可复现关键路径。缺口是缺少统一健康状态、事件滞后、队列丢弃、候选精确率、验证失败率等指标，也缺少结构化 tracing 和一键诊断包。

**下一步：** 为每次观察分配 run id，记录输入快照、耗时、候选数量、跳过原因和错误分类；提供 `observer status --json` 与 health check；在不泄露源码/密钥的前提下导出诊断包。

## 8. Claude Code 与 Codex 的接入差异和可借鉴点

> 本节讨论的是 cyClaw 的接入架构，不推断或宣称两个产品的内部实现细节。

### Q34：Claude Code 和 Codex 都有项目说明、MCP、技能或 Hook，cyClaw 还应怎样集成？

**参考回答：** 两类 Coding Agent 都可以使用 cyClaw 的 MCP 来读取上下文、查看候选、预览和审批 Patch；项目级技能或会话 Hook 可以作为“提醒和管理入口”。但它们不能成为知识发现的唯一来源，因为 Agent 会话不知道人工编辑、其他工具运行和进程离线期间的变化。

因此统一架构是：

```text
Observer：独立数据面，负责发现与证据化
MCP：受控读写控制面，负责查询、审阅、Patch
Skills / Hooks：交互编排面，负责在合适时机提醒
IDE 插件：可视化与生命周期承载面
```

### Q35：Codex 接入有什么巧妙之处？

**参考回答：** Codex 擅长当前任务的代码阅读、修改与验证，cyClaw 不应再让它重复解释任务或当检索代理。通过 stdio MCP 暴露最小上下文、候选和事实治理工具，Coding Agent 只在需要时读取控制面；Observer 在它完全未调用 MCP 时仍持续工作。项目级 skill 可以约束“先读取事实，再执行受控治理”，但不会承担常驻采集。

**工程意义：** 这避免“工具必须被模型记得调用才有价值”的脆弱耦合，也避免 cyClaw 与 Coding Agent 竞争代码编辑权限。

### Q36：Claude Code 接入有什么不同？

**参考回答：** Claude Code 的会话 Hook 更适合作为会话开始时展示待处理知识、会话结束时做轻量收尾的交互点。cyClaw 已将 Hook/MCP 视为辅助管理入口，而非自动写文档引擎。即使 Hook 未执行、会话异常结束或开发者没使用 Claude Code，Observer 仍可根据项目事件工作。

**应避免的错误设计：** 把 `session-stop` 等 Hook 当作唯一沉淀触发器，或允许 Hook 根据模型输出直接改项目文档。这会遗漏非会话变更，也把模型不确定性变成不可见写入。

### Q37：从这两个工具的产品形态中，cyClaw 最应借鉴什么？

**参考回答：** 借鉴“最小上下文、明确权限、可观察执行、把项目约束靠近仓库”的思想，而不是复制某个产品的命令或记忆文件。cyClaw 自己的独特点应是：

1. **事件与认知分离：** 先用确定性事件建立证据，再决定是否需要模型审阅；模型故障不丢失原始变化。
2. **发现与治理分离：** 自动发现可以积极，自动改文档必须保守；候选不等于事实，事实不等于对项目文件的写入。
3. **时间维度是一等公民：** 证据可验证、事实可被取代、Patch 可撤销，避免知识库只增不减。
4. **控制面与数据面分离：** MCP/Skills/Hooks 可替换，Observer 和 Fact Ledger 不依赖某一家 Coding Agent。

## 9. 终面追问：大上下文和下一代 Agent 下还需要 cyClaw 吗？

### Q38：模型原生支持百万甚至千万上下文后，cyClaw 是否失去价值？

**参考回答：** 不会自动失去价值。窗口解决“装得下”，不解决“哪些信息可信、是否仍有效、如何跨会话审计、哪些历史应该被取代或删除”。全量上下文还会带来成本、延迟、权限泄露和注意力稀释。cyClaw 的长期价值是项目知识的版本化、证据化和治理，而不是把更多字符塞进 Prompt。

**前提：** 如果 cyClaw 只剩静态关键词检索和文档生成，它会被大上下文和原生记忆替代；因此必须把投资放在自主事件采集、事实验证、评测和跨 Agent 一致性上。

### Q39：Coding Agent 长期记忆的最终形态是什么？

**参考回答：** 不会是单一向量库或单一 Markdown 文件，而是分层系统：原始事件保留审计价值，结构化事实携带证据与状态，检索索引负责召回，策略层决定能否写入/使用，任务上下文编译器控制进入模型的信息。向量、图谱、文件和原生 Agent memory 都可以成为其中的存储或访问层；真正难的是时效、冲突、权限和评测。

## 10. 面试中必须主动承认的技术债

| 优先级 | 缺口 | 为什么重要 | 建议动作 |
| --- | --- | --- |
| P0 | Observer 状态文件非原子写、无损坏恢复 | 崩溃可能造成状态丢失或解析失败 | 临时文件 + fsync + rename，解析失败回退全量补偿 |
| P0 | 无持久事件队列与 ack | 文件事件在长运行期间仍可能漏检 | 事件账本、幂等键、cursor/ack、低频校验扫描 |
| P0 | 报告识别偏文本启发式 | 易误报/漏报，难定位失败根因 | JUnit/Surefire/pytest/cargo 等结构化适配器 |
| P1 | Prompt Injection 防护不完整 | 不可信仓库文本可能污染模型审阅 | 来源信任级别、输入分区、输出 Schema、红队用例 |
| P1 | 缺少离线标注集与效果指标 | 无法证明候选、对账和召回质量 | 建立金标数据集、指标门禁、试点仪表盘 |
| P1 | 本地锁不支持分布式协作 | 多机并发会产生语义和写入冲突 | 版本号、中心化账本、租约和服务端幂等 |
| P2 | 部分旧文档/扩展描述漂移 | 面试与用户会获得相互矛盾的信息 | 以定位文档为准，增加文档漂移 CI 检查 |

## 12. 一句话收尾

“我不把 cyClaw 描述成已经完成的通用 Agent 平台。它当前最有价值的工程选择，是把自主事件采集、证据化事实、保守治理和可恢复 Patch 分开；下一阶段的成败取决于能否补齐持久事件语义、结构化报告适配、注入防护和可量化评测。”
